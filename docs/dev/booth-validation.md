## 브라우저와 독립 검토

실제 브라우저에서 닉네임 참가, 펀드 100,000원 청약, 99.806375좌 전량 환매, 현금·보유·거래 기록의 서버 반영을 확인했다. 1440px 데스크톱과 390px 모바일 레이아웃, 6종목 송출 화면과 참가 QR도 확인했다.

별도 검토자가 발견한 중요한 문제 3건은 실패 재현 후 수정했다.

1. 응답이 2.5초 걸릴 때 2초 폴링이 모든 성공 응답을 버리던 문제: 같은 조회 키의 주기 요청은 중복하지 않도록 수정.
2. 다른 탭에서 계좌를 바꾸면 이전 화면의 주문이 새 계좌로 전송되던 문제: 저장소 변경 동기화, 열린 주문 무효화, 요청 세션 고정, 제출 직전 토큰 확인을 추가.
3. 늦은 참가 응답이 복구한 계좌를 덮어쓰던 문제: 인증 세대 검사와 참가 중 복구 비활성화를 추가. 늦은 로그아웃과 다른 탭 토큰 삭제도 함께 보호.

느린 폴링, 다중 탭 변경, 저장소 이벤트 전 제출, 참가 중 복구, 늦은 참가·로그아웃, 다른 탭 토큰 삭제의 7개 회귀 테스트가 실패 후 통과했다. 기존 조회 훅 검사와 합쳐 13개 통과, 전체 UI 165개 통과를 확인했다. 검토의 보류 사항과 미해결 중요 문제는 없다.

## 구현 결정

사용자가 승인한 설계에 따라 추가 계획 승인 없이 현재 세션에서 구현했다. 별도 관리 작업 공간은 정적 허용 경로 밖이어서 그 작업 공간에 한정해 파일 작성·테스트 권한 확장을 사용했다. 제품 동작에는 영향이 없다.

이전 앱은 URL /legacy로 재해석하는 대신 서버의 study 모드와 별도 지연 로딩 청크로 보존했다. 이전 이벤트 화면을 함께 운영하려면 study 모드 배포를 사용한다. 현재 기본 배포와 QR은 booth 모드다.

## 30초 갱신 변경

사용자 요청으로 신규 장의 시세 갱신을 10초에서 30초로 변경했다. 펀드 운용은 계속 30초이며 화면 조회는 2초다. 50분 장은 100구간, 운석은 계속 20:10, 귀신 사건은 개장 60초 이후·마감 30초 이전·최소 90초 간격이다. 지연 거래 차단은 3회 갱신 주기인 90초다. 이미 열린 구버전 장은 저장된 이력과 사건 번호를 보존한다.

신규 회귀 검사로 29초 미갱신·30초 첫 갱신, 100회 후 마감, 사건 간격, 20:10 운석, 구버전 장 호환을 확인했다. SQLite 전체 409개와 UI 전체 165개, ruff/mypy/build가 통과했다. 75개 장 시뮬레이션도 30초 주기로 다시 실행해 위 표를 갱신했다.

PostgreSQL에서도 갱신·장 운영·사건 일정·QA 검사 15개가 통과했다. 미리보기 서버를 새 코드로 재시작하고 실제 HTTP로 30초 진행 시 version 0→1, 공개 시각 16:00:30, 장 상태 open을 확인했다. 이전 QA DB는 보존하고 별도 미리보기 DB를 사용했다.

## PR #3 리뷰 반영

P2 지적 네 건을 재현한 뒤 수정했다. 보안 컨텍스트가 아닌 HTTP 환경에서는 getRandomValues로 주문 ID를 생성하며 동일 주문 재시도에 같은 ID를 쓴다. 배경 조회 실패 때 마지막 스냅샷과 진행 중 주문창을 유지해 주문 응답 유실·중복 체결을 막는다. 탭의 storage 이벤트는 현재 저장소 값을 읽어 메모리 상태에만 반영하므로 오래된 이벤트가 최신 계좌를 덮어쓰지 않는다. 예약 귀신 사건과 관리자 뉴스·사건은 같은 구간에 함께 발표하고 가격 충격을 복리로 합성한다.

주식·펀드 HTTP 주문/재시도, 조회 실패 중 주문 성공/실패, 지연된 토큰 변경·삭제·clear 이벤트의 화면 회귀 검사 7개와 뉴스·수동 사건 충돌의 서버 검사 2개가 수정 전 실패 후 통과했다. 추가 검토에서 발견한 저장소 쓰기 실패 회귀도 빈 저장소·기존 토큰 저장소의 2개 실패 재현 후 보완했다. 저장 실패 시 메모리 로그인을 유지하고 공유 저장소가 나중에 변경되면 새 값·삭제를 반영한다. 최종 SQLite 전체 411개, UI 전체 174개, ruff/format/mypy strict/TypeScript/Vite 빌드가 통과했다.
